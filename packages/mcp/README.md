# Lepidus MCP server — design & usage

The Model Context Protocol (MCP) server that makes the Lepidus Design System
**queryable by AI coding assistants** — Claude Code, Cursor, Windsurf, or any
other MCP-capable client. Instead of guessing component APIs from training
data, the assistant asks the design system directly and gets ground truth.

## Why it exists

AI assistants are a primary consumer of this design system, alongside human
developers. They need three things to produce on-brand code reliably:

1. **Rules** — what to do and never do (`llms.txt`, `CLAUDE.md`)
2. **Facts** — exact component props, class names, token values (the
   component manifest)
3. **A way to look facts up mid-task** — this server

The first two are static files an agent reads once. The server covers the
third: while generating a page, the agent can ask "what props does Table
take?" or "which token is the danger border?" and get the current answer.

## Architecture

```
component-manifest.json ─┐
tokens.css (built)       ├──▶ server.mjs ──▶ stdio (newline-delimited JSON-RPC)
llms.txt                 ─┘                   ▲
                                              │ .mcp.json wires the client
                              Claude Code / Cursor / any MCP client
```

- **Zero dependencies.** The MCP stdio transport is newline-delimited
  JSON-RPC 2.0; the server implements `initialize`, `tools/list` and
  `tools/call` directly (~200 lines, `server.mjs`). Nothing to install.
- **Build artifacts as the source of truth.** The server reads
  `public/component-manifest.json` (generated by `npm run manifest` from the
  TypeScript types + the CSS class inventory), the generated
  `packages/tokens/build/css/tokens.css`, and `public/llms.txt`. It never
  parses source code at request time — answers are fast and consistent with
  what's deployed.
- **Read-only.** The server cannot modify the design system; it is purely a
  reference surface.

## Tools

| Tool | Input | Returns |
|---|---|---|
| `list_components` | — | Every component with availability (plain CSS block name and/or React) and a one-line description |
| `get_component` | `name` (e.g. `"Button"`) | Full JSON reference: props with types/defaults/descriptions, plain-CSS class inventory, import line. Fuzzy-suggests on a miss. |
| `search_tokens` | `query` (substring) | Matching CSS variables with values **per theme** — searches names and values, so `"#1c4599"`, `"radius"`, and `"button-primary"` all work |
| `get_usage_rules` | — | The full `llms.txt` rules document |

## Wiring it up

This repo ships a [.mcp.json](../../.mcp.json) at the root, so **Claude Code
picks the server up automatically** when opened in this project:

```json
{
  "mcpServers": {
    "lepidus": { "command": "node", "args": ["packages/mcp/server.mjs"] }
  }
}
```

To use it from a *product* repo (where Lepide developers actually work), copy
that block into the product repo's `.mcp.json` and point `args` at a checkout
of this repo (or a vendored copy of `packages/mcp` + the three data files).
For Cursor, the same JSON goes in `.cursor/mcp.json`.

## Keeping it fresh

The data files are rebuilt by the normal pipeline:

```bash
npm run tokens      # tokens.css
npm run css         # class inventory inputs
npm run manifest    # component-manifest.json (also runs before Storybook builds)
```

CI builds Storybook on every change, which regenerates the manifest — so the
deployed copy at
`https://lepidus-design-system-button.vercel.app/component-manifest.json`
is always current even if a local checkout is stale.

## Testing

The server is plain stdio — test it with a pipe, no client needed:

```bash
printf '%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"t","version":"0"}}}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_component","arguments":{"name":"Button"}}}' \
 | node packages/mcp/server.mjs
```

## Extending

To add a tool: append a definition to `TOOLS` (name, description, JSON
schema) and a case to `callTool()`. Good candidates as the system grows:
`get_pattern` (page-level composition markup), `get_icon` (the 129-icon
library), `validate_markup` (lint HTML for off-system classes/colors).
